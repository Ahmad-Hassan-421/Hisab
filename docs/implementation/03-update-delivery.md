# Hisab in-app update delivery

The connected C51 runs `com.example.hisab` 1.0, build 1, installed from Android shell. The installed APK is debuggable. Its signing certificate SHA-256 is `d2dc29853f3cc5ce5ed1456e613da764baf20a408d5148c913ea48d784bce285`. The local Android keystore can sign with the same identity. The APK pulled from the device and the earlier archived 1.0 APK have different file hashes, so the device copy is the reference for testing.

The installed 1.0 binary already calls `https://hisab-onlo.onrender.com/api/releases/latest`. Its code compares the returned Android `versionCode` and forwards `downloadUrl` to its updater. Both properties are preserved in the response. No GitHub tag or release existed when inspected. Hisab 1.1.0 build 2 is now published as `v1.1.0`. [GitHub release](https://github.com/Ahmad-Hassan-421/Hisab/releases/tag/v1.1.0)

The signing workflow creates `hisab-update.json` and `SHA256SUMS` from the signed, versioned APK. The backend checks that the manifest matches the GitHub tag, package, exact asset URL, size, and SHA-256 digest reported by GitHub. Both release endpoint paths remain available. With no published release, the backend returns HTTP 204 and the new client shows the current-version state. Releases are optional.

The new Android updater compares the actual Android version code, uses the exact Hisab GitHub APK path, and checks the recorded size and SHA-256 before verifying APK identity, signing certificate, version name, and version code. It shares the verified copy from app-private storage with Android’s normal installer. A reopened app reads its installed build from the new binary after an upgrade. The older updater can read the compatible server response but does not gain the new checksum verification retroactively.

The C51 QA app checked a release, retried a failed check, dismissed an optional update, measured and cancelled a download, rejected a wrong checksum, and opened Android’s installation flow for the matching signed candidate. The test returned before changing Android permissions or installing the candidate. Separately, Android accepted a local, non-debug `1.1.0` candidate signed with the matching key over the exact APK copied from the C51 on the emulator. The package retained its original installation timestamp and opened its main activity after the update. That test used Android’s package manager directly. Phase 11 separately verified data retention in the Room migration using a disposable profile and ledger entry.

The published tag points to `2f99a49288419ca5ceee08026856659d8c85cdf3`, which passed both required CI workflows. GitHub recorded all three asset hashes. A fresh public download matched the 18,405,504-byte APK and SHA-256 `ef034d9895df980f3372658d1e61c59750a7f2213ca64e008c88a3f3ad110132`. Android’s `apksigner` verified the downloaded APK and its certificate. Both live update endpoint paths returned HTTP 200 with the same version, URL, size and checksum. The C51 owner still needs to approve the normal Android install and confirm the existing Hisabs are present afterward.
