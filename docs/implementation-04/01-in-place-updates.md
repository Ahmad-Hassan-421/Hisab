# Preserve the Hisab installation during updates

The C51 had one installed or retained Hisab package in its Android user: `com.example.hisab` 1.1.0 build 2. It had one launcher activity, and the APK matched the signed GitHub release. Its first install timestamp predates the update. Before this phase, the separately installed QA package used the same launcher label as production, so a QA install could look like a second production Hisab. The C51 had no QA package during the inspection. That means the earlier report cannot be attributed to a specific installation with certainty.

Production remains `com.example.hisab` with the Hisab label and existing signing identity. QA uses `com.example.hisab.qa` and the Hisab QA label. Ordinary development builds now use `com.example.hisab.debug` and the Hisab Debug label. Android debug builds cannot replace production. The QA updater accepts its configured loopback origin only, and production accepts the exact GitHub release asset path. Production rejects debuggable update APKs even where the installed signing certificate would otherwise match. The installer still asks Android to perform the update with user approval.

CI now checks package, launcher label, launcher count and whether the APK is debuggable. The release job also requires a newer build number, a matching tag, and the expected signing certificate before publishing. The next candidate is 1.2.0 build 3. It is for local verification until the release phase.

If more than one icon appears, inspect Android’s App Info or use `adb shell pm list packages com.example.hisab` to identify each installation. Keep `com.example.hisab` for production. Check who owns the data in any test package and whether any local-only records need to be retained before removing it. The packages have separate Android storage, and installing the production update does not transfer the other package’s private data.

The final build passed 34 Android JVM tests, debug and unsigned release builds, and lint with zero errors and 101 warnings. Android tooling checked the release and QA APKs, and the ordinary debug variant reported the `.debug` application ID. The release validation rejected a QA APK. The locally signed 1.2.0 APK matched the installed certificate and Android accepted it as an update to 1.1.0 on the emulator. Build 3 opened with one installed production package and one launcher activity. The first-install timestamp matched the last reading before the update. Two overlapping attempts to install the emulator baseline prevented a reliable UID comparison, so the C51's already completed 1.0 to 1.1.0 in-place upgrade provides the independent device evidence. The emulator test used the Android package manager and did not exercise the production update button, sign-in, or profile and ledger continuity with 1.2.0. Those checks remain part of release validation.
